# 21 - Custom Settings, per-map rates and the rules register

Since Update 1.5.3 the game has a native server settings framework, and players can read its values in game on the
**Custom Settings** screen. This is the largest change to self-host configuration since launch, and the one we get
asked about most. This doc covers where the settings live, how to keep them through a Funcom update, how to give one
map its own rates, and how we keep what players are told in step with what the server runs.

Everything here was observed on builds `2111270` (1.5.3) through `2168446` (1.5.15.3). Funcom adds, removes and
renames keys in hotfixes, so diff the template on every update (below).

## The files

All of these live on the BattleGroup's persistent volume, reachable through the FileBrowser pod. They survive a
Funcom image update. Image contents do not.

| File | What it holds | Shown to players |
|---|---|---|
| `Saved/UserSettings/UserServerCustomSettings.ini` | The 1.5.3 settings framework: rates, costs, XP, combat, building limits. **Yours.** | Yes, on the Custom Settings screen |
| `Saved/Config/LinuxServer/ServerCustomSettings.ini` | Generated by the server at boot | No (it is output) |
| `Saved/UserSettings/UserGame.ini` | Game subsystems: PvP partitions, security zones, Landsraad board, inventory base size, sandstorms, Coriolis | No |
| `Saved/UserSettings/UserEngine.ini` | `[ConsoleVariables]` cvars: mining multipliers, PvP resource bonus, and many more | No |
| `Saved/UserSettings/UserOverrides.ini` | Highest-precedence layer | No |

Rules we learned the hard way:

- **`DifficultyLevel=Custom` must be set** in the user file. With any preset, the preset overrides every key.
- **Since 1.5.3.1 the generated file only carries the keys your user file does not set.** That is normal. A
  generated file with five keys in it is not a failure.
- **Some comments in the template are wrong.** `WaterExtractionRate` is a rate: higher is faster, whatever the
  comment says. We set `0.5` meaning "faster" and doubled the time instead. Measure a change in game before you
  announce it.
- **Settings stack across files.** `GatheringAmount` in the settings file and the two mining cvars in
  `UserEngine.ini` (`Dune.GlobalMiningOutputMultiplier`, `Dune.GlobalVehicleMiningOutputMultiplier`) multiply each
  other. 3 on top of 3 read as roughly 9x for cutteray and vehicle mining. Pick one lever per thing and set the
  other to 1.0.
- **Do not double a lever that moved.** 1.5.3 added `FuelBurnTimeMultiplier`. If you doubled fuel before 1.5.3
  with the `dw.FuelBurningMultiplier` cvar, a leftover 2.0 there on top of a native 2.0 gives 4x. When a native key
  replaces an old lever, retire the old one in the same change.
- **The screen is not always the server.** Some values are enforced by the client. We raised the active Landsraad
  contract limit on the server and players still saw 3. Check what a player sees before you publish a number.
- **A player can reset their own view.** On 1.5.15.x, a player who opens the Custom Settings screen and presses
  Cancel sees the sub-fief limit drop to the stock value until they relog. The server value is unchanged.

## Funcom's template and the re-base

Every server download ships a template at `scripts/setup/config/UserServerCustomSettings.ini`, with the section
header, `DifficultyLevel=Custom` and every key at its stock value. Between hotfixes Funcom adds and removes keys
(1.5.3.3 removed one we were setting), and renames sections in the other files (1.5.3 renamed the Landsraad
`Data=` line in `UserGame.ini` to `DedicatedServerData=`, and the old name was silently ignored).

Our user file **is** the template with our values overlaid, every key explicit. On an update that changes the
template, we re-base:

1. Stop the fleet. This runs only in the zero-pod gap of a maintenance window: the server writes these files at
   boot.
2. Diff the new template against the previous build's. Read every added, removed or renamed key.
3. Copy the new template beside the user file, and overlay your value set on the copy: replace each key's line,
   whether it is active or commented out in the template.
4. **Gate, and abort on any failure with the live files untouched:**
   - every key of your value set exists in the new template (a typo or a removed key would otherwise vanish
     silently);
   - every key the old user file set comes out with the same value, unless it is in your value set (a changed value
     must be deliberate);
   - the file has its section header and `DifficultyLevel=Custom`.
5. Back up both files, swap the copy in, start, and read both files back after boot.

Keep the value set in one place (we keep it in the re-base script) and make every other copy follow it.

## Config watch

A setting in a file is not a setting in effect, and a Funcom update can revert a file you did not think it touched.
After every update, and on a timer, we compare the four `UserSettings` files key by key against a manifest of
values of record:

- Funcom's stock files are recorded per build automatically, so a new build needs no approval step.
- Any changed, missing or unexpected key in your files is listed in the ops channel and fails the unit.
- A deliberate tuning change updates the manifest in the same change as the setting. Otherwise the watch reports
  your own change as drift, and people learn to ignore it.

`scripts/dune-config-hash.py` is the tool. Run it last on update day, after the settings are verified, and before
you reopen.

## Per-map rates

The settings files are shared by every pod. To give one map its own value, put an `-ini:` argument on that map's
pods in the BattleGroup CR. For a Custom Settings key the argument is:

```text
-ini:ServerCustomSettings:[/Script/DuneSandbox.UserServerCustomSettings]:GatheringAmount=1.5
```

Where it goes:

| Target | CR location |
|---|---|
| One partition of an always-on map (a Hagga sietch, a Deep Desert instance) | `.spec.serverGroup.template.spec.sets[<set>].podSpecs[]`, an entry `{index: <partition id>, arguments: [...]}` |
| Every pod of an instance set (ecolabs, dungeons, story maps) | the set-level `arguments` list |

Rules:

- **A podSpec change recycles that pod on its own.** On a base map that is a restart, so do it in a maintenance
  window, in the zero-pod gap, or confirm that map is empty right before the patch.
- **Patch with compare-and-swap.** Read the CR, build a JSON patch that tests the exact current values and the
  object uid, then applies. A stale read then fails instead of overwriting someone else's change.
- **Keep the shared default at 1.0** and put the whole per-map number in the argument, so there is one lever per
  map.
- **Read the arguments back from the CR**, with a jsonpath on `.spec`. Do not read them from the pod's process
  arguments or logs: those also carry credentials.
- **Know what drops them.** On our host, updating through Funcom's battlegroup update command replaced
  `director.ini` with stock and lost a per-pod argument. We now move image tags ourselves ([08](08-updates.md)).

The PvP zone bonus is separate: `SecurityZones.PvpResourceMultiplier` in `UserEngine.ini` multiplies harvest inside
PvP zones on every map. Funcom's default is 2.5. On a full PvP map that covers almost the whole map, so quote it
with the base rate: our full PvP sietch is 1.5x base, 3.75x in the open.

## The rules and rates register

Players ask what the server runs. Discord pins, the website, the portal rules page, the in-game screen and your own
memory will all disagree within a month unless one file is the source and every other surface is a copy.

The method:

1. **One register file**, one row per player-facing rule: the rule in plain words, the value live now, the mechanism
   (which file or CR location), and whether the Custom Settings screen shows it.
2. **"Live now" means live.** Flip it after the change is verified on the server, never when it is planned.
3. **A change history**, newest first, with the date and the reason (poll result, owner decision, Funcom change).
4. **A publication tracker:** every surface that repeats a rule, how to change it, and its state. Nothing changes on
   the server without the tracker being swept in the same session.
5. **Polls for anything players feel.** We put rate changes to community polls and publish the result as the rule.

### Our values, as the example

Snapshot at build `2168446`. These are ours, not a recommendation.

| Rule | Value | Mechanism |
|---|---|---|
| Generator, turbine and wind trap fuel | 2x run time | Settings `FuelBurnTimeMultiplier=2.0` |
| Harvest yield (hand, cutteray, vehicle) | Habbanya 1.5x, Amtal 1.5x (3.75x in the open), Deep Desert PvE 1.5x, Deep Desert PvP 2.5x, instances 1.5x | Per-map `GatheringAmount` arguments; shared cvars at 1.0 |
| PvP zone resource bonus | 2.5x (Funcom default) | `UserEngine.ini` `SecurityZones.PvpResourceMultiplier` |
| Inventory volume | 2x (Amtal 4x and 100 slots) | Settings `InventoryVolumeMultiplier`; Amtal per-map arguments |
| Water extraction | 1.25x faster | Settings `WaterExtractionRate=1.25` |
| Building piece budget | 1.5x | Settings `BuildingPieceLimitMultiplier=1.5` |
| Sub-fiefs per player | 5 | Settings `FiefdomLimit=5` |
| Character XP, Intel, Landsraad multipliers | stock, with double XP weekends instead ([23](23-events-runner.md)) | Settings, 1.0 each |
| Combat, survival, crafting, costs, durability | stock | Settings, 1.0 each |
| Landsraad board | 6 contracts per voting block, 15 min repeat, 35 daily tokens | `UserGame.ini` Landsraad `DedicatedServerData` |
| Double dungeon loot | on | `UserEngine.ini` cvar |

We moved most 1.5.3 keys away from stock in the first week, then rolled them back after player feedback and put
every further change to a poll. "Play as before the update, then vote" was the right call for an established
community.
